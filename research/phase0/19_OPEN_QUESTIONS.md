# Open Questions and Required Spikes Before Architecture Freeze

## Status key

- **P0 blocker:** a wrong answer changes the kernel, distribution boundary or security model.
- **P1 design input:** architecture can be outlined, but the answer is required before its subsystem is frozen.
- **P2 defer:** useful evidence that can wait until after the core contracts are stable.

This is a research backlog only. No spike in this report has been executed.

## P0 blockers

| # | Open question | Why the references do not answer it | Future evidence/spike | Exit criterion |
|---:|---|---|---|---|
| 1 | What exact user-facing purpose and capability set defines Kinetic Play Core? | OpenDroid's broad autonomy depends on `Eco_reference/opendroid/app/src/main/java/com/opendroid/ai/accessibility/OpenDroidAccessibilityService.kt`; OpenClaw instead stubs mobile UI in its Play source set and adds it only in `apps/android/app/src/thirdParty`. A generic “autonomous agent” label is insufficient for permission/policy design. | Freeze representative Core user journeys, map each to public Android API/AppFunction/intent/provider, and obtain a formal Play policy review. | Every launch workflow has an API path and capability classification; no critical Core success metric depends on general LLM-driven accessibility. |
| 2 | Are Play and Advanced separate application IDs/signing/update channels, or variants of one product identity? | OpenClaw proves source-set separation in `apps/android/app/build.gradle.kts`, but does not settle data sharing, store listing or upgrade semantics for Kinetic. AndyClaw/OpenDroid combine powers in one app. | Compare product-flavor, separate-app and companion-app designs for manifests, signing, shared data, migration and user comprehension. | A signed distribution ADR proves Advanced code/permissions cannot appear in Play artifacts and defines migration/interoperability. |
| 3 | What is the exact durable run/effect state machine? | OpenDroid persists plan snapshots but leaves execution/approval continuations process-local in `core/agent/AgentLoop.kt`; OpenClaw Android outbox and host tasks use different state models; Hermes persistence is transcript-centric. | Specify transitions and invariants for `Run/Step/Attempt/Effect/Delivery`, then model-check/property-test crash points on paper/prototype in a later phase. | Every transition has one owner, transactional persistence rule, restart action and terminal/unknown outcome; no effect requires a suspended coroutine to recover. |
| 4 | How will each non-idempotent capability reconcile an unknown outcome? | OpenClaw `src/provider-runtime/operation-retry.ts` avoids retrying creates, but the references do not provide a universal Android effect reconciliation layer. | Classify initial tools as idempotent, idempotency-keyed, status-queryable, compensatable or manual-reconcile; design examples for send message, calendar create, file mutation and app action. | Every effectful Core tool has an explicit retry/reconcile/compensation/user-escalation contract. |
| 5 | What local model meets the minimum structured-agent quality on target phones? | OpenDroid `LiteRTLMProvider.kt` is real embedded inference, but catalog hashes/sizes are incomplete and its stream error contract is flawed. AndyClaw Llamatik is opaque/GPL-context; AirLLM is workstation research. None supplies Kinetic task-quality/device results. | Benchmark at least one LiteRT-LM model and one clearly licensed GGUF/mobile alternative on low/mid/high target devices: load RAM, TTFT, tok/s, structured-call validity, tool-task success, thermal and battery. | A model/device matrix meets predeclared latency, quality, memory, thermal, license and coverage thresholds. |
| 6 | What is the provider streaming and fallback contract when partial output exists? | OpenDroid emits some LiteRT failures as text; its wrapper avoids replay after emitted content. Hermes/OpenClaw have provider-specific repair/fallback branches. | Define typed stream events and inject faults before first token, after content, during tool arguments and after usage; compare local/cloud route changes. | No error is represented as successful text; fallback cannot duplicate content/effects or silently weaken privacy/locality policy. |
| 7 | What is the minimal deterministic capability descriptor/policy lattice? | OpenDroid `ActionDefinition`, AndyClaw `ToolDefinition`, OpenClaw policy evidence and Hermes registry each omit different mobile security fields. | Specify candidate descriptors and evaluate 15–20 representative tools against permissions, scopes, targets, sensitivity, confirmation, network, foreground, idempotency and audit. | The schema can express every initial tool without escape-hatch maps/strings, rejects unknown fields, and proves policy monotonicity. |
| 8 | How should user confirmation bind to mutable real-world targets? | Reference approvals are largely action/command based. Contacts, accounts, documents and app state may change between plan, dialog and execution. | Design canonicalization/resolution for contact, package/signature, URI grant, account and remote resource; test time-of-check/time-of-use and process-death cases. | Approval digest and display identify the actual target; any meaningful target/argument change invalidates it. |
| 9 | Is Android AppFunctions sufficiently available and capable to be a first-class launch dependency? | Official research summarized in `10_ANDROID_CAPABILITY_POLICY_MATRIX.md` shows an experimental preview, Android 16+/compile SDK 36+ requirements and limited end-to-end availability. No local repository implements it. | Build a future isolated provider/consumer proof on supported devices/emulators: discovery, schema fidelity, caller identity, confirmation, cancellation, errors and fallback. | Decide `primary`, `optional accelerator`, or `future` with an API-level/device coverage plan and no Core dead end. |
| 10 | What extension model is both useful and defensible? | AndyClaw's active raw Binder/provider/broadcast/intent system and unfinished AIDL skill system are inconsistent (`AndyClaw/.../extensions` and `app/src/main/aidl`). OpenClaw/Hermes plugins are trusted host code. | Threat-model built-in, AppFunction, separately signed IPC and remote/MCP providers; define publisher identity, versioning, scope attenuation and revocation. | One typed invocation lifecycle survives malicious caller/provider tests and does not require dynamic code in Core. |
| 11 | Can a constrained Skill IR cover enough real OpenClaw/Hermes workflows? | Counts in `13_SKILL_AND_PLUGIN_COMPATIBILITY.md` show many skills mention shell, Python, Node or external CLI even when the package contains only `SKILL.md`. | Select a stratified 30-skill corpus; manually compile semantics into a candidate IR and classify exact loss/required native tools. | A predeclared share of high-value workflows maps without arbitrary code; unsupported semantics fail visibly and safely. |
| 12 | How will learned skills be validated rather than merely authored? | Hermes `agent/learn_prompt.py` says there is no separate distillation engine and asks the live agent to write `SKILL.md`; background review can mutate durable knowledge. | Define evidence references, simulation fixtures, success/failure scoring, user review, rollback, expiry and version invalidation; run adversarial learning scenarios. | A learned workflow cannot gain authority, activates only after evidence/tests/approval, and can be explained/reverted. |
| 13 | What is Kinetic's sensitive-data routing and retention policy? | References can place conversations, memory, screenshots, accessibility trees, contacts and notification content into prompts/logs/trajectories. Hermes redaction is rich but regex-based; OpenClaw audit is metadata-only. | Inventory data classes and flows across local/cloud model, memory, logs, analytics, backup, export and deletion. Threat-model prompt injection and provider error paths. | Every data class has an explicit at-rest, prompt, network, retention, backup, audit and deletion rule with a user-facing control. |
| 14 | What remote interoperability is actually a product requirement: OpenClaw Gateway, generic MCP, both or neither? | OpenClaw protocol is mature but very broad; MobileRun/AnyClaw MCP exposes desktop-authority tools. Supporting all early would distort the native domain model. | Choose concrete interoperability journeys and test only the necessary methods/transports/auth identities against a small adapter schema. | A bounded versioned subset has owners and conformance tests, or interoperability is explicitly deferred without affecting native contracts. |

## P1 subsystem design inputs

| # | Open question | Local evidence | Future evidence/spike | Exit criterion |
|---:|---|---|---|---|
| 15 | Which UI perception modes belong in Core versus Advanced? | MobileRun `mobilerun/agent/droid/state.py`, `mobilerun/tools/ui/state.py`, screenshot provider and coordinate tests support tree + screenshot modes; OpenClaw's robust accessibility snapshot/action code is third-party flavor; app-owned vision is different from cross-app automation. | Compare app-owned semantic nodes, screenshots/vision, AppFunctions and advanced accessibility on a fixed task set. | Typed snapshot/viewport contract and capability availability matrix with measured grounding accuracy and privacy cost. |
| 16 | What coordinate/target identity survives rotation, foldables, multi-window and IME changes? | MobileRun's `tests/test_android_vision_coordinate_contract.py` and related tests establish multiple spaces; OpenClaw validates UI epoch/package. Neither covers Kinetic's device matrix. | Device/instrumentation matrix with rotation, density, inset, fold, split-screen, scrolling, IME and screenshot crop transformations. | Stale/wrong-space targets fail closed; transform round trips meet declared error bounds. |
| 17 | What voice surface is feasible without pretending to be a system assistant? | OpenClaw Android uses `SpeechRecognizer`, audio capture and TTS/voice coordinator; OpenDroid/AndyClaw add foreground/listening services. None proves broad OEM/default-assistant behavior. | Prototype push-to-talk, foreground conversation and optional VoiceInteractionService role on supported devices; measure latency, interruptions and background restrictions. | One Core UX has predictable lifecycle/permissions; system-assistant integration is separately classified and optional. |
| 18 | Which proactive workflows remain useful under WorkManager/FGS/alarm limits? | OpenClaw/Hermes cron semantics are server-like; AndyClaw heartbeat auto-approval is unsafe; OpenDroid service execution is not durable. | Map representative reminders, summaries, syncs and monitoring to Android scheduling primitives; test Doze, reboot, force-stop, standby bucket and denied notification permission. | Each workflow states latency SLA, eligibility, user visibility, battery budget and behavior when execution is delayed/blocked. |
| 19 | What model-router policy balances quality, privacy, cost and offline behavior? | Hermes/OpenClaw have broad provider routing/fallback; OpenDroid hybrid provider combines on-device options but is not a full policy router. | Replay the same task corpus across local/cloud models with privacy labels, costs, structured validity and failure injection. | Deterministic route policy with explicit user controls; local-to-cloud escalation never happens implicitly for sensitive data. |
| 20 | What embedding/retrieval stack fits Android constraints? | OpenClaw memory host supports external/native Node embeddings; OpenDroid has basic Room memory and local model hooks; Hermes retrieval/providers are desktop Python. | Compare Room FTS/BM25, small on-device embedding model and hybrid retrieval for quality, index size, latency, energy and sensitive-data behavior. | Selected baseline meets retrieval accuracy/latency/storage goals on minimum device; embedding remains optional if lexical meets MVP needs. |
| 21 | How should memory poisoning and stale knowledge be detected? | Hermes fences/sanitizes memory context and tracks some provenance/usage; OpenDroid memory lacks strong evidence/expiry semantics. | Adversarial corpus with injected external instructions, contradictory preferences, expired app procedures and deletion requests. | Retrieval exposes evidence/version/sensitivity; stale or untrusted records cannot silently become system authority. |
| 22 | What is the supported Android/device floor? | OpenClaw Android uses minSdk 31/target 36; OpenDroid minSdk 26/target 35; AndyClaw minSdk 35 and privileged hardware. Local model availability varies more than API level. | Define low/mid/high device profiles across API, RAM, storage, ABI, accelerator and OEM; run lifecycle/model/media tests. | Published capability degradation matrix and a minimum Core device profile with no hidden advanced dependency. |
| 23 | How are downloadable model files authenticated, licensed and updated? | OpenDroid `ModelDownloadWorker.kt` supports resume and SHA when supplied, but many registry hashes are empty. AndyClaw downloader lacks checksum/license metadata. | Define signed catalog, immutable content hashes, size/quota, atomic import, parser validation, model card/license acknowledgement and rollback. | Corrupt/swapped/truncated/unlicensed artifacts cannot activate; storage cleanup/update is crash safe. |
| 24 | What backup/restore behavior is correct for secrets, memory and pending work? | OpenDroid `SecurePrefs.kt` may recreate after key loss; OpenClaw device identity currently serializes encrypted private key bytes. References do not establish Kinetic restore rules. | Test Auto Backup/device transfer/credential invalidation/keystore reset; classify each database/file/key. | Restored app never replays approvals/effects or exposes unusable secrets; user gets explicit reauthentication/recovery UX. |
| 25 | What is the audit/trajectory split and storage budget? | OpenClaw `src/audit/audit-event-types.ts` is metadata-only; MobileRun trajectories/screenshots are rich but sensitive and not correctness-critical. | Define minimal journal, privacy audit, opt-in debug trajectory and benchmark export schemas; size a long-running workload. | Correctness records are non-droppable; content/artifacts are encrypted, bounded, expiring and user-controlled. |
| 26 | Which Android app integrations need package/signature-specific adapters? | OpenDroid often falls back to intents/accessibility and package discovery; MobileRun app cards are untrusted prompt guidance. | Select top apps and classify public intent/provider/AppFunction/deep-link support, package signatures, version ranges and localization. | Each adapter has a documented supported version/risk/test fixture; unsupported apps do not trigger generic unsafe fallback. |
| 27 | What cancellation UX and semantics are understandable? | OpenClaw/Hermes distinguish cancellation/timeouts; AndyClaw can orphan streamed tools; Android effects may already be dispatched. | User studies plus injected cancellation at model, approval, executor and delivery phases. | UI distinguishes stopped, cancelling, effect completed and outcome unknown; no false “cancelled” claim. |
| 28 | What dependency injection and module boundaries minimize startup/resource cost? | OpenDroid uses Hilt; OpenClaw Android uses more manual/runtime composition; AndyClaw application initialization owns many heavy services. | Measure cold start and lazy construction on a skeleton in a later foundation phase after contracts freeze. | Expensive model/media/provider/advanced modules are lazy and profile-separated; DI choice does not leak into domain contracts. |

| # | Question | Reason to defer |

| 34 | Which UI/HUD aesthetic and onboarding narrative is best? | Architecture only needs permission/profile/transparency requirements; visual system can follow product research after capabilities are honest. |

## Recommended spike order for the next phase boundary

No later-phase work is authorized by this report, but the evidence suggests this decision order:

1. Freeze Play Core journeys and profile/distribution boundary (#1–2).
2. Specify durable effect state and capability policy/approval (#3–8).
3. Benchmark embedded local inference and provider stream/fallback contract (#5–6, #19, #22–23).
4. Test AppFunctions/extension and UI-target contracts (#9–10, #15–16, #26).
5. Validate Skill IR and learning lifecycle (#11–12).
6. Complete data/memory/audit/backup policy (#13, #20–25).
7. Validate Android background/voice/device behavior (#17–18, #22, #27–28).

Architecture freeze should not be based on feature-count parity with the references. It should be based on measured task journeys, recoverable effects, explicit policy boundaries and a supported-device/distribution envelope.
